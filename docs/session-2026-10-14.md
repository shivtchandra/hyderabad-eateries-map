## 2. Speed

**Diagnosis (measured on the live site):**
- Page HTML was already fast (Cloudflare, 0.05 to 0.4 s).
- The slow part was data. On a cache miss, `/api/theme/current`, `/api/votes` and `/api/leaderboard` each took 1.5 to 1.8 s.
- The Vote tab called `/api/theme/current` 3 times at once.
- `/api/theme/history` read each past theme's votes one after another, up to 40 database calls in a row.
- `/api/leaderboard` was never cached because it carried the user's ID.
- Opening on Vote or You still downloaded the map code (MapLibre, about 1.5 MB) and `recommendations.json` (2.3 MB).

**Fixes:**

| Change | File |
|---|---|
| Edge cache is now stale-while-revalidate: visitors get the cached copy at once and it refreshes in the background (copies kept 24 h) | `api-worker/src/index.js` |
| Google login token is shared across worker instances, so a new instance skips about 400 ms | `api-worker/src/firestore.js` |
| Past themes' votes are read in parallel | `app/api/theme/history/route.js` |
| Leaderboard split in two: the cached top list, plus a small live `?uid=…&me=1` request for your own rank, both in parallel | `app/api/leaderboard/route.js`, `lib/leaderboard.js` |
| Repeat theme requests share one network call | `lib/themeVoting.js` |
| Map code only loads when the Map or Route tab is shown | `app/page.jsx` |
| `recommendations.json` waits until the browser is idle unless the app opens on Map | `app/page.jsx` |
| Jumps to a spot (from Vote, search or a `?spot=` link) wait until the map is ready (`flyMap`) | `app/page.jsx` |

**Result after deploy:** every API route answered in 0.04 to 0.05 s once cached, down from 1.5 to 1.8 s. The first request after a deploy is still slow while the cache fills.

## 3. Card rail tap

**Before:** tapping a card in the bottom rail opened the details popup straight away.

**Now:**
- First tap moves the map to that spot's pin and highlights it, with no popup.
- A second tap on the same card opens the details.
- Tapping a pin or another card in between resets this, so the next tap only moves the map again.

Files: `app/components/CardRail.jsx`, `app/page.jsx` (`handleSelect` with `opts.fly`)

---

## 4. Newsletter: not sending

- Sign-ups work. The opt-in after you vote posts to `/api/subscribe`, which stores the address in Firestore `subscribers` with a consent record. Unsubscribe links work.
- **No emails are sent.** There's no email service and no scheduled job. People who sign up get nothing until a sender is built.

## 5. Deploys

**How it works:**
- Pushing to `master` deploys both the site (`.github/workflows/static-site.yml`, Cloudflare Pages) and the API server (`.github/workflows/api-worker.yml`, Cloudflare Worker `mapmyhyd-api`).
- The site also rebuilds daily at 06:15 IST.
- Running the site workflow on any branch still publishes to production (it deploys with `--branch master`).

**What we did:**
1. Committed and pushed the work above to `redesign-atlas` (3 commits).
2. Deployed the API server by hand from `api-worker` (`npm run deploy`). The Cloudflare login needed a few tries; the first browser login failed because Chrome sent back an old, expired approval.
3. Merged `redesign-atlas` into `master` (no conflicts, done in a separate worktree so uncommitted local files weren't touched) and pushed. Both workflows ran and the site deploy succeeded.

**Still uncommitted locally (not shipped):** `app/spot/[id]/page.jsx`, `data/venue-content.json`, `lib/inspectionsServer.js`, `public/featured.json`, `data/inspection-drives.json`.
